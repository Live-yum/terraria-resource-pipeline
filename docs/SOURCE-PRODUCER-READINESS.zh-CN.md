# 从真实来源到 13 角色：剩余闭环与交付门槛

本表区分已经实现的消费转换、有限静态事实、待实现的来源生产和真实环境验收。已有 13 个派生角色不等于 13 个真实角色已可发布；当前真实完整消费组仍为 0。`DERIVED_ONLY`、条件初始化器证明、运行时观测、发布审批是不同层级，不能互相替代。

现有后端 schema 2 仍固定要求 110 项广义完整 claims。本表的 13 个消费角色不会改变该门禁。任何消费基线专用合同都必须另行显式设计、独立审核、标明证据类型和 UI scope；当前没有实现这样的新合同，不能借本表放宽旧 complete 标志或审批。

## 固定边界

- 目标客户端/服务端：已确认同来源的 Windows 1.4.5.8；完整源哈希见来源绑定文档。
- 已实现的静态增量：ID/本地化原文等局部元数据；有限研究模型；前缀饰品增量、九系数、初始池；三个 Count 数值界和七个初始 item-group 数组。后几项有正常返回、依赖绑定模型、核心库语义和无干扰前提，不认证最终运行时状态。
- XNA 官方字节可从固定 Microsoft 分发包作为数据核验，当前不需要让用户猜测或上传三个 XNA DLL。静态字节可得不等于已验证混合模式/native 启动。
- 简体中文是现有应用明确使用的显示文化；fallback 与替换命令仍须按来源规则实现。普通世界/难度/特殊种子状态若没有明确应用政策，应列为 profile 决策，不能暗中定义“完整”。
- 不在助手环境中执行游戏 EXE/CLR。可执行采集器必须是用户明确选择后，在隔离环境由用户运行的有界观察程序。

## 逐角色矩阵

| 消费角色 | 已实现 | 来源生产仍需完成 | 最终验证 |
|---|---|---|---|
| items.catalog | 独立域 join、七列格式、跨对象绑定 | 固定 profile 的最终 Item defaults、有效名称/persistent/research 联合生产；Count 界不等于可选 ID 集合 | 预期/实际/重复/缺失 ID 及完整 app/backend 合同 |
| items.rules | 全字段结构与分类依据；有限前缀效果/系数/池/组事实 | Item/recipe/dye 初始化后的完整 gameplay 字段、最终排除/排序注册表和适用性策略 | 每字段均有值与来源，不能用默认补洞 |
| items.categories | 应用分类算法及真实应用差分测试 | 接入同一个完整 items 事实集与固定应用 policy | 与应用原算法逐行相等 |
| materials.base | 命名行转换、基础哈希 | 地图所有选项颜色/名称、paint 输入、独立域和明确 map-option 选择政策 | 完整 ID/选项覆盖，颜色不从图片猜测 |
| materials.rules | 布局/shape/variant 格式及引用校验 | TileObjectData 布局与 item-placement join；应用 shape/variant/优先顺序 policy | 无缺失布局或悬空引用；特殊形状对照 |
| pixel.catalog | 候选展开、float32 调色与指纹 | 真实材料基础与经过审核的应用白名单 | 与基础字节/政策指纹一致 |
| pixel.rgb | 完整 256³ 精确索引、实际应用生成器差分 | 接入上一行的真实基础输入 | 全字节对照与扫描线完整性 |
| markers.catalog | 格式、材料绑定、选择器结构 | 当前版本 selector/帧裁切 policy 从应用和来源规则生成 | 每项 selector、位置、名称都有可追溯规则 |
| markers.images | 新 PNG 裁切、spacing2/gapless 拼图 | 接入同一 policy 与真实源纹理 | 原始纹理哈希、尺寸、像素比对 |
| player.presentation | 展示 registry/分类引用与验证 | buff/dye/hair/wing/equipment/selection facts 和应用显示政策 | 三对象 items 基础绑定、完整 registry 域 |
| player.walk | 14 帧配方合成、裁切、palette/zlib | 从实际 source/app 帧和层规则生成配方；不能让用户手填未知配方 | 每帧像素、层顺序与策略来源对照 |
| player.atlas | 图集、别名和修复结构 | 装备 slot/变体/裁切/局部修复映射生成 | 每个引用都落到明确源纹理与帧 |
| worldgen.choices | schema/default/目录投影与基础绑定 | Hook 配置/权威目录与后端 schema/revision 源适配、部署版本选择 | 当前服务合同、schema revision 和允许目录一致 |

`worldgen.options` 是服务配置草稿，不是第 14 个发布角色。后端已具有 `worldgen-schema.json` 和 `WorldGenerationSchema.metadata()`；版本列表由部署目录库存产生。应读取并绑定这些已拥有的来源，不应由 vanilla 游戏程序集猜测业务 schema。

## 有界观察采集器，不证明所有世界状态

完成地图有限模型后，应把重点转为一个明确版本和 profile 的用户本地观察采集器，而非不断证明整场游戏：

1. 固定 Windows x86、CLR/依赖来源哈希、调用入口/token/签名、profile 状态、文化与输出 schema。输入不允许指定任意命令/方法/插件。
2. 独立短生命周期隔离环境：游戏输入只读，无网络、无游戏存档/用户凭据挂载；仅私有结果目录可写，配置 CPU/内存/时间/文件数量/输出体积上限。完整客户端启动或图形初始化若必要，必须明确列出，不能伪装成“纯读取”。
3. 实现完整 Item/recipe/dye/material/player-registry 初始化与字段读取流程。每个调用点和所读字段都必须实际存在、被固定版本签名绑定；未知步骤是开发缺口，不得标为 NOT_RUN。
4. 输出有限 JSON/图像字节，不序列化任意 CLR 对象、不调用任意 ToString。记录真实依赖绑定、调用步骤、profile、独立预期域、覆盖缺口和内容摘要。
5. 运行结果标为 profile 内的运行时观测。两次独立进程一致是复现性证据，不是所有 seed/difficulty/player 状态证明，也不替代发布权利和审批。
6. 由新适配层直接把这些事实与已固定的 app policy 送入全部组装器。不会让用户手写未知字段、补空表或选择任意旧输出冒充新提取。

## 可以交给用户“只做真实测试”的停止条件

以下条件必须全部满足，才可以作出该交付表述：

- 所有来源采集、命名/引用 join、配方生成、服务 schema 接入代码均已实现；没有用 placeholder、空列表或旧 payload 代替未知事实。
- 观察程序能够从源代码构建；协议、隔离启动配置、失败路径、退出清理和来源不匹配拒绝均有原创夹具测试。
- 固定入口/字段/依赖/初始化步骤的静态存在性与签名检查通过；不要求证明所有可能的游戏状态，但不能留已知缺失调用或未实现依赖装载。
- 每个 profile 明确预期域；所有角色的完整 join 和跨组引用检查已实现，任何缺口会拒绝整套发布。
- 私有 13 角色套件通过实际消费者与后端验证，并有来源、policy、producer/domain 证据和原子 release-set 绑定。
- 所需的人类 policy 决策已明确。若应用代码没有固定世界变体基线，应让用户选定；实际本地执行仍需要用户明确 opt-in。
- 审批/鉴权/CDN 读回/微信或其他设备渲染的真实验收清单完整。这些未运行阶段才可标 NOT_RUN；未实现的生产逻辑必须继续标 IMPLEMENTATION。

人物特殊 VFX 的现有应用渲染保真限制单独列出：完整数据不自动补齐应用未移植的着色器/特效。这不应被混写成来源字段缺失，也不能假称已经实现。
